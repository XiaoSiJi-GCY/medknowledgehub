# 存储职责、版本发布与缓存失效

## 各组件保存什么

| 组件 | 保存内容 | 是否权威状态 |
| --- | --- | --- |
| PostgreSQL | 用户、授权、知识库、文档版本、Chunk、任务、结构化记录、查询及反馈 | 是 |
| Milvus | Dense 向量、BM25 稀疏索引和过滤元数据 | 可重建的检索投影 |
| Neo4j | 实体与带 Chunk/版本出处的关系 | 可重建的检索投影 |
| Redis | Celery 队列、任务结果与检索缓存 | 不作为文档权限真值 |
| 文件系统 | 原始文件、解析产物 | 原始资料与重建输入 |

表定义集中在 `app/models.py`。`app/storage/database.py` 用 SQLAlchemy Session 组织事务；`migrations/` 保存可追踪的 Alembic 结构变更。

## 当前版本是怎样确定的

Document 表保存 `active_version_id`。Version 有版本号、来源机构、发布日期、生效日期、失效日期、解析器与状态。新版本的 Chunk、向量和图关系先写好，再在事务中切换指针，旧版本退出当前检索范围。

若两个版本并行处理，后完成的旧版本不能覆盖已经发布的新版本。外部索引没有跨数据库分布式事务；系统通过先写投影、后发布、幂等写入和可重试清理控制一致性。

版本有效性受当前指针、状态、生效日期、失效日期以及文档/知识库停用状态共同约束。发布日期只用于来源说明，不等于生效日期。原文与版本对比接口仍允许有权限的读者查看历史资料。

## 删除与归档

停用文档会立即清空其当前指针，后续检索不再使用它；归档知识库同时停用其中的文档。外部索引可由 `cleanup_indexes` 任务清理。原始文件与元数据保留，方便追溯；当前没有用户界面的恢复入口和自动硬删除策略。

## 缓存为什么不会一直返回旧内容

每个知识库有 epoch。发布、权限变更或归档会改变范围签名；缓存键还包含用户、版本列表、查询与模型配置。命中缓存后仍回到 PostgreSQL 校验证据，不把 Redis 内容当作授权依据。模型嵌入缓存按模型和文本的内容指纹去重，避免重复付费。

## 学习实验

运行 `test_lifecycle.py`，理解失败更新为何不影响旧版本。然后手动更新一份资料，查看 Document 指针、Version 状态和 epoch。最后对比 `scope()` 的过滤条件与 Milvus/Neo4j 中的元数据，找出哪一层负责最终排除失效内容。
